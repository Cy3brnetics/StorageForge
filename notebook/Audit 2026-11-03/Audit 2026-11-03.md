# Audit 2026-11-03: unsigned scripts and auth on new routes

**Short version:** fix [[SF-44 Security key can be removed or replaced without touching it|SF-44]] and [[SF-45 deploy.apply removes the sentinel that security.emergency guards|SF-45]] before shipping. No script that runs as root through a deploy goes out unsigned, and every new route needs a session and has a permission rule. The problems are in what those permissions allow: new protections can be reached around with a lesser permission, the same pattern the 2026-10-31 audit found.

| 0 | 2 | 4 | 8 | 14 |

**Status:** open. Unit suite: 946 tests, all pass, 23 skipped. PostgreSQL and the KVM lab were not run.

**Update, 2026-11-03:** 13 findings fixed in the working tree, not committed, and [[SF-48 Signed scripts run unsigned commands on a second host|SF-48]] partly: its second hop remains. Unit suite after the fixes: 988 tests, all pass, 23 skipped. Still not run: PostgreSQL (including migration 037), the KVM lab, and a real browser for the changed panels. The tables below show findings as they were found.

## The three to read first
1. [[SF-44 Security key can be removed or replaced without touching it|SF-44]]: someone holding a session and the password can delete the security key, or add their own, without the touch the key exists to demand.
2. [[SF-45 deploy.apply removes the sentinel that security.emergency guards|SF-45]]: an operator cannot change the sentinel's settings, but can uninstall it from a host. Decided: the sentinel gets its own permission.
3. [[SF-48 Signed scripts run unsigned commands on a second host|SF-48]]: the one place a signed script issues root commands on another machine with no signature there.

**Run without a fresh signature, but delivered signed:** job, task, schedule, sentinel, ClamAV and identity timers run programs a signed deploy installed. The job key's `--serve` forced command works the same way. See [[EQ-09 The signing promise reads wider than the code\|EQ-09]].

**Not sent by StorageForge:** downloads a person runs (`/api/*/script`, `install-script`, `cron`, `bundle`, `/api/security/compliance/script`, `/api/map/designs/<id>/export`, `/api/deploy/setup-script`), and the CLI commands `schedule run` (`cli.py:1112`, on the server) and direct scans (`cli.py:85`).

**Not covered by the signature:** a signed run's stdin (`deploy.py:414`). Today that is only data: YARA rules, base64 path lists, backup and restore streams. It travels over SSH to a checked host key, and no script executes it.

1. **SF-44:** put the touch on key changes. It is small, and it makes the other step-up routes mean something.
2. **SF-45:** decide who may remove the sentinel, then add it to `need_for_deploy`.
3. **SF-46:** same pattern, same fix: give policy changes the permission the direct route has.
4. **EQ-07:** widen the safety tests, so the fixes above and the next new routes are held by a walk over the list.
5. **PF-31:** give the routes that take large bodies their limits.
6. **SF-47**, then the Low findings in any order.
7. **SF-48:** the largest job. Do it when the send and receive steps are next touched.

## What was done well
Keep these when fixing.
- **Default-deny held.** All 135 new route entries have a rule, and the walk tests forced the fresh-password and audit decision for each.
- **The signature covers what matters:** host, machine id, time, a nonce claimed atomically, args and script, in its own SSHSIG namespace. Evidence signing uses a separate namespace, and the runner refused a request signed in it.
- **Values reach Bash as data.** A hostile `$(...)` value through the hold, release, relabel, clean room, measure and sentinel install generators produced no runnable code. The two lines the check flagged print the script's own word `CANARY`, not the value.
- **`sentinel.conf` is only safe because of the validator:** `REPORT_URL` lands raw in a file root sources, and `REPORT_URL_RE` refused all five hostile URLs tried. Don't loosen that pattern.
- **Falco rules cannot end their heredoc.** The check runs after the macros are filled in.
- **The report token** is new each deploy, stored as a hash, and kept in a 0600 file on the host.
- **Docker scans never read `.Config.Env`,** so container secrets stay off the wire.

## Scope and method
- **Baseline** `31fc091`, **head** `d78881b`, tree clean, so there was no uncommitted work to include.
- **Run:** the unit suite (946 tests, 23 skipped), bandit, a no-session sweep of every route, a role matrix, a call graph from routes to host paths, the real runner against forged requests, and proof scripts on throwaway SQLite databases using the project's stand-in test host. Scripts and results are outside the repo, and no real host was touched.
- **Bandit:** both High results are SHA-1 used to make display ids (`canvas.py:21`, `payloads.py:23`), not security, so neither counts. Its 115 Medium results were not triaged beyond the two shown at the end of its output (SQL built from fixed strings, and a literal `0.0.0.0` in a parser).
- **Call graph limits:** it follows direct calls and module-qualified names, so a function passed as a value is not followed. A first looser version gave false GET hits from shared names, which were checked and dropped.
- **Read in full:** `routes_security.py`, `routes_secplus.py`, `routes_infra.py`, `routes_clamav.py`, `webauthn.py`, `permissions.py`, the runner and `run` in `deploy.py`, `access.sudo_run`.
- **Read in part:** `security.py`, `secplus.py`, `secscripts.py`, `gitrepos.py`, `runtimes/docker.py`, `netfacts.py`, `jobscript.py`, `scriptkit.py`, `changes.py`, `tasks.py`, the route changes in `server.py`.
- **Not read:** `steps_infra.py` beyond the nft helpers, `whatif.py`, `reach.py`, `mapdesign.py` beyond the export and save paths, `infragraph.py` beyond the firewall and history paths, `updates.py` beyond its deploy path, the new browser code beyond a search for unsafe HTML (none found), the lab tiers.
- **Not run:** PostgreSQL and the KVM lab. Both databases have migrations 029 to 036 with the same tables, compared by name only. Nothing here was proven on a real distro. [[SF-45 deploy.apply removes the sentinel that security.emergency guards|SF-45]] and [[SF-46 Operators can apply legal holds through retention policies|SF-46]] were proven against stand-ins, not real ZFS or systemd.
- **Checklists:** the [[Security checklist]] was applied to the new routes and generators. The [[Feature and design checklist]] was applied only to the features above, so the life-cycle walks were not done, and this audit does not vouch for those features beyond its focus.
- **Earlier fixes re-checked:** [[SF-41 Remote nodes overview rewrites authorized_keys on GET and blocks on offline nodes|SF-41]] (no GET reaches a host) and [[SF-42 Same-origin fallback omits port comparison on cross-origin requests|SF-42]] (`same_host_and_port` compares the port) both hold.
