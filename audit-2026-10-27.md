# StorageForge audit: QoL, gaps and next features

**Date:** 2026-10-27
**Scope:** `storageforge-indexer` code (backend, web UI, generated scripts) and the running container `storageforge-storageforge-1`.
**Method:**
- Static analysis: ruff (bugbear, security and pylint rules), vulture, and pip-audit against the packages installed in the image.
- Data and memory checks: row counts and memory use measured on the live data (6.1M files), plus a separate read-only container to time the heavy analyses.
- Code review of every feature added in this session, and of how the features fit together.
- Earlier findings: a re-check of `audit-results.md` (2026-10-26).

## Summary

The container is healthy and well hardened: read-only root, all capabilities dropped, non-root user, secrets from files, and no known vulnerabilities in any installed package. The open items fall into three groups:

- **Four real bugs.** Two are in how the planner and the new shares feature round-trip the design. Two are in how the scheduler names and starts scans.
- **Operations.** There is no database backup, even though the SSH keys live in the database. The 1 GiB memory limit is hit constantly. Nothing is ever pruned.
- **Untracked work.** The project has a git repository with a single `init` commit, and all of this session's work is uncommitted.

## 1. Bugs (fix first)

| # | Problem | Evidence | Fix |
| :- | :--- | :--- | :--- |
| B1 | **Saving a host in the planner loses data from its shares.** It drops each export's `fromScan` flag and its "Mount on" clients. | `planner.js:981` reads only protocol, name, path, clients and options, and `planner.js:581` writes back only those. | Carry `fromScan`, `mounts` and any unknown keys through the planner untouched. Better: pass through every field the planner does not edit. |
| B2 | **A deployed share shows up twice and the "Deploy" button never clears.** The scan reports `NFS /srv/media` and the design says `NFSv4.2 media`; `merge_intent` matches on (protocol, path, name), so they never match. | Reproduced with `blueprint.merge_intent`: four exports where there should be two. | Match NFS shares by path and SMB shares by name, comparing only the protocol family. When a scanned share matches a design one, keep the design's extra fields (such as `mounts`) and mark it deployed. |
| B3 | **One host gets two scan jobs under two names.** The scheduler queues by key-binding pattern (`10.42.0.100`), while "Scan now" uses the hostname (`cachyos-x8664`). The duplicate check compares strings, so both run; the second fails with "already being scanned" or, before the guard, "database is locked". The Scans tab also shows IPs. | `server.py:128`, `:178` and `:378`. Scan #40 failed `/` and `/home` with "database is locked". | Turn every request into one host identity (via `connect_address` and the hosts table) before queueing, and show hostnames. |
| B4 | **Every restart rescans every host straight away.** The scheduler queues before its first sleep, so each rebuild means about 5 minutes of heavy I/O on cachyos-x8664, even right after the last scan. | `server.py:_schedule`. | Skip hosts scanned within the interval (`hosts.last_scanned_at`), and space out the first run. |

## 2. Operations and the container

| # | Finding | Detail | Suggestion |
| :- | :--- | :--- | :--- |
| O1 | **No database backup.** | `index.db` holds the encrypted SSH keys, bindings, designs, move plans and audit log. If the volume is lost, the keys go with it. There is no `backup` command. | Add `storageforge-index backup` using SQLite's online backup to `/app/data/backups`, run it nightly from the scheduler, keep the last N, and add a restore command. Document that `secrets/vault_secret` must be backed up separately. |
| O2 | **The 1 GiB memory limit is hit constantly.** | `memory.events max = 142,381` with no OOM kills yet. Process memory is 339 MiB during a scan, and the Cleanup analyses add up to 335 MiB more (measured: duplicates 12.6 s and 335 MiB peak; cold data 8.5 s). The rest is reclaimable SQLite cache. | Raise `deploy.resources.limits.memory` to 2g. Also see U4: work the analyses out once after each scan, not on every request. |
| O3 | **Nothing is ever pruned.** | `file_changes` has 516k rows. `scan_denied` keeps a full copy for every scan, and `scans` and `scan_jobs` grow forever. The database is 3.2 GB. | Keep changes for N days or N scans, and `scan_denied` for the latest scan only. Run `PRAGMA optimize` after scans and add a monthly `VACUUM` option. |
| O4 | **Dependencies aren't pinned.** | `pyproject.toml` uses `>=` ranges and there's no lock file, so rebuilds can pull different versions. All current versions are clean (pip-audit). | Add a hashed lock file (pip-compile or uv) used by the Dockerfile. Remove leftover images: `storageforge:test` (254 MB) and one dangling image. |
| O5 | **Work isn't committed.** | `/home/archie/Projects/storageforge/.git` has one commit; about 30 files are modified and about 15 are new. | Commit in logical chunks (scans/LVM, access, shares/git, moves, UI) so a regression can be bisected. |
| O6 | **The request log is noisy.** | Every request is printed, including the 3-second `/api/jobs` polling and static files. | Log only `/api` calls that change things, plus errors, or add `STORAGEFORGE_ACCESS_LOG=0`. |
| O7 | **PostgreSQL is untested.** | Migrations 004–007 were written for both databases, but only SQLite was exercised (same as M-05 in the earlier audit). | Add a CI job that runs the test suite against a Postgres container, or drop Postgres support. |

## 3. Security (still open from the 2026-10-26 audit)

- **H-01, no roles:** every signed-in user can generate keys, install them on hosts, deploy shares and download move scripts. This is fine while you are the only user. Add viewer, operator and admin roles before anyone else gets an account.
- **H-02 and M-02, rate limits:** the login counters are in memory and reset on restart. Keep the failed-attempt count in the `users` table with a short lockout.
- **M-04 is resolved for the container:** the entrypoint requires `session_secret`.
- **New since then and reviewed:** the read-only scan access (capability-limited `find`/`sha256sum`), the read-only rsync sudoers rule, one-time sudo passwords over SSH stdin, and the generated scripts (report-first, only-add, never delete). These hold up. The scripts were exercised in Debian containers for copy, verify, cutover, rsnapshot, git mirror, NFS/SMB server and client.

## 5. Features worth adding

Ranked by value for this setup (Archie, TR01 and three Pis):

1. **Progress from scans for moves and shares.** The generated scripts already write `/var/lib/storageforge/moves/<plan>/<step>.done` and `.cutover`. Have the scan read those files, so each step in the Moves tab shows "copied 2026-10-27 · verified · cut over" without any tracking by hand. Deployed shares already come back as scanned shares once B2 is fixed.
2. **Detect backups and snapshots automatically.** 3-2-1 protection is entered by hand today. Scans can recognise:
   - restic repositories (`config`, `data/`, `index/`, `keys/`, `snapshots/`) and borg repositories (their README marker), found the same way as bare git repos;
   - snapshot configs from snapper, timeshift, btrbk and sanoid, plus btrfs snapshot subvolumes;
   - rsnapshot roots.

   This would fill the sync, snapshot and backup columns, and their age, with real data.
3. **Disk health.** SMART data (`smartctl -j -a`, behind a narrow sudoers rule like the rsync one), btrfs device error counters, and the date of the last btrfs or ZFS scrub. Show them on disk boxes in the topology, and flag disks that are failing or haven't been scrubbed recently.
4. **Capacity history and forecast.** Store each mount's used bytes per scan. Show a small trend on mount boxes and estimate when each will be full ("`/mnt/data01` full in about 140 days").
5. **Notifications.** Send ntfy, Gotify, Discord-webhook or email alerts for failed scans, offline mounts, disks over 90% full, backups past their age, SMART warnings and repositories that are behind.
6. **Schedules per host.** Pis hourly, cachyos nightly, quiet hours, and skip on battery for laptops. This replaces the single global `STORAGEFORGE_SCAN_INTERVAL`.
7. **Roles (H-01)**, once anyone else uses it.

## 6. Checked and fine

- **Container:** healthy with 0 restarts, a 238 MB image, `/tmp` and `/run/storageforge` on tmpfs (empty at rest), and SQLite temp files on the data volume.
- **Dependencies:** Flask 3.1.3, Werkzeug 3.1.9, cryptography 50.0.2, waitress 3.0.2, Flask-Login 0.6.3 and Flask-Limiter 4.1.1, all with no known advisories.
- **Static analysis:** of 65 ruff findings, none are real bugs. They are path constants, SHA-1 used for stable IDs, and closures called inside their loop. Clean-ups: an unused `datetime` import in `payloads.py`, an unused `MOUNTABLE_FS` import in `report.py`, and a no-op conditional at `graph.py:163`.
- **Tests:** 60 pass. There are none for the browser code; the UI was checked by hand in the browser.
