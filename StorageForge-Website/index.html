Know every disk before you touch one

StorageForge knows what's on all your Linux machines. It logs in over SSH, records every disk and file, and shows you the whole layout in one place. When you want to change something, it checks your plan first, then writes a script that tells you what it would do before it does it.

Install on your machinesNothing

No agent and no service. It logs in over SSH and runs tools Linux already has. The one exception is deploys, which add a small runner on the machines you pick.

What it needsAn SSH key

It keeps the key encrypted. You decide which machines it can reach.

What it knowsWhere it all is

The name, size, age and location of your files on every machine, plus how the disks fit together. It stores this on your server. It doesn't store file contents.

What it won't doSurprise you

A scan changes nothing. A script only reports until you tell it to act. Wiping a drive has to get past three separate locks.

Storage knowledge shouldn't live in one person's head

On a handful of Linux machines, the storage layout usually lives in shell history, an old wiki page and somebody's memory. That holds up until a disk fails or a copy lands on the system drive because a mount was missing.

You've probably never used a tool like this, so here's the short version. Monitoring tells you a disk is full. Backup tools copy what you point them at. Configuration tools apply what you describe, without knowing what's on the disk. None of them can tell you whether your plan is a bad idea.

StorageForge can. It keeps a searchable record of every machine and checks your plan against it before anything runs.

What it does

One web UI and one CLI, from finding a file to deploying a mirror job.

See the whole layout

The topology draws each host's disks, pools, datasets, mounts, links and shares, with lines between them. Hardware comes from the scan. Tiers, protection and exports are yours to edit, and they survive rescans.

  • Right-click almost anything for its actions
  • Force-directed graph and a Files map of copies between hosts
  • Markdown architecture reports and Obsidian .canvas export

Find anything on any host

Patterns such as *.cr2 or *invoice*2024* answer from the index, filtered by host, folder, size or age. A separate role can use search and nothing else.

  • What changed between scans
  • Duplicate folders, even renamed ones, and checksum duplicates
  • Cold data, listed by the age of each folder's newest file

Plan changes like a playbook

Stage folder, btrfs, ZFS, LVM, mount and drive tasks in order, each on its host. The check walks the plan so later tasks see what earlier ones create, and flags a formatted pool member or a mount over folders that hold files.

  • Download as Bash or an Ansible playbook
  • The planner designs a host from bare disks, with a RAID calculator

Build storage jobs from blocks

Tasks are small programs on one host, by hand or on a systemd timer: guards, conditions, rsync, rotating backups, snapshots and service restarts. Each block is checked against the index as you edit.

  • Runs take a lock, so they never overlap

How it works

Reading and changing are separate paths. Scans use the tools a Linux install already has. Changes arrive as scripts you can read first.

Your hosts
  • find, findmnt, lsblk, df
  • zpool, git, docker when present
  • storageforge-run and storageforge-job, only on hosts you set up for deploys
Between them
  • ssh → hostRead-only scans, with a key from the vault
  • signed script → hostDeploys, each for one machine and valid 10 minutes
  • host → run reportJob results and state
StorageForge, one container behind nginx
  • Scanner, then an index of every file and folder
  • Designs, the graph, topology and reports
  • Plans: changes, moves, shares and tasks
  • Encrypted key vault and audit log

  1. Scan

    A bound key connects and reads the host under nice and ionice. Each scan is diffed against the last, and a failed walk deletes nothing from the index.

  2. Look

    Topology, search and inventory answer from the index and never open a connection, so browsing puts no load on your hosts.

  3. Design

    Mark what a scan can't know: tiers, protection, exports and links. Hardware refreshes on rescan and your intent stays.

  4. Plan

    Stage changes, moves, shares or a task. Each step gets ok, warn or crit as you edit.

  5. Act

    Download the script and run it yourself, or deploy it from the UI. Either way it reports first and changes things only when asked.

  6. Rescan

    The next scan shows the result and flags drift if something deployed was changed by hand.

Built for machines you can't afford to break

StorageForge holds keys that reach every host, and can run root scripts on hosts set up for deploys. These rules apply across the product.

Report first

A script run with no options only reports. Changing things takes a mode flag such as --apply or --run.

Three locks on drives

The device typed twice in the plan, --destructive on the command line, and a refusal to touch anything mounted, swapped on, or part of RAID, LVM or LUKS.

Trash is a rename

Trash goes to .storageforge-trash/<date>/, a moved source becomes <name>.migrated-<date>, and fstab is restored if verification fails.

Safe to rerun

Every step looks before it acts, so a rerun after a failure picks up where it stopped.

Keys stay encrypted

AES-256-GCM under an Argon2id-derived key. Each task decrypts its key into locked memory and hands it to a short-lived ssh-agent on tmpfs.

Signed deploys

The host runner checks the signature, machine id, age and a one-use nonce. The deploy key alone runs nothing.

A name proves nothing

Hosts are pinned to their SSH host keys. A machine claiming an indexed name is refused and audited.

An audit log you can verify

Every connection, scan, sign-in and deploy is chained with an HMAC. audit verify finds an edited, deleted or reordered row.

A fresh password for host commands

Anything that runs on a host from the web UI asks again unless you typed your password in the last 5 minutes.

A hardened container

Non-root, read-only root filesystem, all capabilities dropped, and images pinned by digest with dependencies pinned by hash.

Who it's for

  • Home lab owners with a NAS, a few servers and a mix of btrfs and ZFS
  • Small teams that run their own Linux storage and want it written down
  • Consultants looking after several clients, each on an isolated site with its own keys

What to know first

  • Keep it off the internet. It holds SSH keys that reach your machines, so run it on your LAN.
  • It only manages Linux machines. Alpine can be scanned, but not deployed to.
  • It shows the last scan, not this second. Scans run every 6 hours by default, or whenever you start one.
  • It only sees what the scan account can read. An optional setup step lets that account read everything without scanning as root.
  • It's early. It's at version 0.2.0 with no tagged releases. CI hasn't run on a runner yet, and the lab tests go through the API, so they don't cover the web pages.

The tools doing the work

StorageForge doesn't replace your Linux tools. It decides what to run, checks it against the index, then calls the same programs you'd use by hand. That's why you can read every script before it runs.

ConnectingOpenSSH: ssh, a short-lived ssh-agent, and ssh-copy-id to install keys.
Reading a hostfind, findmnt, lsblk and df. It also uses zpool, btrfs, lvs, git and docker or podman when they're present, and sha256sum for checksum scans.
Copying datarsync for copies and mirrors, rsnapshot for rotating snapshots, git clone --mirror for repositories, and btrfs send or zfs send for snapshot streams. duperemove is optional.
Snapshotssnapper, rsnapshot, and native btrfs and ZFS snapshots.
Changing disksparted, mkfs, btrfs-progs, ZFS tools and lvm2, plus findmnt --verify to check each fstab edit.
SharesThe NFS server and Samba, checked with testparm, with firewalld or ufw opened for the listed clients.
Running jobsbash scripts, systemd timers, flock so runs don't overlap, and apt, dnf, yum, zypper or pacman to install what's missing.
Signing deploysssh-keygen -Y signs each script, and a small runner on the host verifies it.
Alerts and exportsntfy, Gotify or a webhook for alerts. Ansible playbooks, Markdown reports and Obsidian .canvas files for exports.
The serverPython with Flask and waitress behind nginx, in Docker. The index is SQLite with FTS5 or PostgreSQL with pg_trgm. Keys are encrypted with the cryptography library, using AES-256-GCM and Argon2id.

Run it with Docker

You need Docker with Compose v2. Hosts need SSH and a user with your public key. Run these from storageforge-indexer/.

docker compose up -d --build
docker compose exec storageforge storageforge-index user add admin
docker compose exec storageforge storageforge-index vault generate --name fleet
# add the printed public key to ~scan/.ssh/authorized_keys on a host, then:
docker compose exec storageforge storageforge-index vault bind --key fleet --host 10.0.20.0/24 --user scan
docker compose exec storageforge storageforge-index scan --host 10.0.20.5

Then open https://<this machine>:8443 and sign in. To try it without a real host, examples/demo/demo.sh runs the whole flow against a disposable SSH target. Read the getting started guide for the details.
