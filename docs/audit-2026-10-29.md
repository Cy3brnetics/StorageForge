This audit was done while writing these docs. It checks the code against the rules in [Concepts](concepts.md#the-rules), and the README against the code. It looks for things that disagree with each other, not for security holes; those are in the [2026-10-28 security audit](../security-audit-2026-10-28.md).

**Scope.** Working tree on `master` at `bc12d9c`, plus uncommitted work from a parallel security session (host-key confirmation, `hostkeys.py`, migration 015, script quoting). Those uncommitted changes are described where they matter and marked *in progress*.

**Tests.** `python3 -m unittest discover -s tests`: 100 tests, 1 failure, 1 skipped (104 after the C1/B1 tests, same result). The failure is environmental (see [T1](#tests)).

**Code changes.** None were made while the docs were written, because another session was editing the same files. C1 and B1 were fixed afterwards, on the same day, in files that session had not touched; everything else is still open.

## Container

**C1. The entrypoint's subcommand list is out of date.** `docker/entrypoint.sh` only sets up the environment (secrets check, migrate, vault) for a fixed list of subcommands:

```sh
scan|search|changes|dupes|hosts|export-markdown|report|vault|audit|graph|canvas|blueprint|migrate|serve|healthcheck|user|-*) ;;
*) exec "$@" ;;
```

Anything else is executed as a raw command. `folders`, `access`, `moves`, `git`, `shares`, `plan`, `deploy`, `docker`, `backup`, `restore` and `prune` are missing. So `docker compose run --rm storageforge restore … --yes`, the README's own restore command, tries to run a program called `restore` and fails. `docker compose exec` is unaffected because it bypasses the entrypoint.

**Fixed.** The list now names every subcommand. Inverting the test was considered and rejected: `docker run … storageforge ls` would then reach the CLI as an unknown subcommand. Instead, `tests/test_consistency.py` compares the list with the CLI's own subcommands and fails when one is missing. Images built before the fix still need `--entrypoint storageforge-index`, as [Operations](operations.md#restore) says.

## Backups

**B1. Essentials backups are missing newer tables.** `backup.ESSENTIAL` is `vault_meta, ssh_keys, key_bindings, users, hosts, blueprints, move_plans, audit_log`. Tables added since then are not in it, though a rescan cannot rebuild them:

| Missing | What a restore loses |
| :--- | :--- |
| `change_plans`, `storage_tasks` | every staged change plan and task |
| `settings` | report URL, alert channels, the "hide example" choice |
| `deploy_access`, `deployed`, `jobs` | which hosts have deploy access and what is deployed. Jobs keep running on their hosts, but their token hashes are gone, so every report is refused (401) until the plan is deployed again. |
| `host_key_confirmations` *(in progress)* | confirmed host keys; passwords are refused until they are confirmed again |

**Fixed.** All of these tables are now in `ESSENTIAL`. Every other table is named in a new `REBUILDABLE` list: the index, graph, scan state, run history, alerts and web sessions. `tests/test_consistency.py` fails when a table is in neither list or in both, and checks that an essentials backup carries a row from each newly added table.

## CLI

**S1. Loopback hosts become local scans.** `cli.py:65`:

```python
local = args.local or host in ('localhost', '127.0.0.1', '::1') and not args.user and not args.key
```

`scan --host 127.0.0.1 --port 2222`, meant for an SSH server published on a loopback port (the demo target, a VM, a tunnel), skips the vault binding for `127.0.0.1:2222` and walks this machine with no SSH, checksumming its files. This happened while preparing the screenshots for these docs.

*Fix:* treat loopback as local only when `--port` is 22 and no vault binding matches, or only with `--local`.

**S2. Broken pipes print a traceback.** In `main()`, `except BrokenPipeError` comes after `except Exception`, which already catches it (and re-raises). `storageforge-index search … | head` therefore ends with a traceback. *Fix:* move the `BrokenPipeError` clause first.

## Plans

**P1. Tasks have no CLI.** Changes (`plan`), Moves (`moves`) and Shares (`shares`) all have `list`/`check`/`script` on the command line; storage tasks are web and API only. *Fix:* a `tasks list|check|script|import` subcommand built the same way.

**P2. Task checks ignore containers.** The Moves and Changes checks call `docker.users_of()` to warn when a step touches a folder a running container uses. Task checks don't, so a task that mirrors into a live database folder gets no warning. *Fix:* the same check in `tasks.check()` for copy and snapshot blocks.

**P3. One feature, three names.** Staged change plans are **Changes** in the UI, `plan` in the CLI (because `changes` already lists file changes between scans), and `/api/changes` in the API. The CLI help explains it, but anyone reading the API next to the CLI meets three names for one thing. Options: rename the file-changes command to `diff` (keeping `changes` as an alias for a release), then rename `plan` to `changes`. At minimum, keep the naming table in [Concepts](concepts.md#names-used-in-these-pages).

**Checked and fine.**
- Deleting a change plan doesn't check deploy state, while Moves and Tasks do. That is right: a change deploy is a one-off script and leaves nothing behind to clean up.
- The script mode flags differ (`--apply` for changes and shares, `--run`/`--install` for moves and tasks), but they follow a rule: `--apply` makes a host match a description, `--run` performs an action. That rule is now written down in [Concepts](concepts.md#the-rules).

## API

**A1. Settings change without a password check.** `PUT /api/deploy/settings` sets the report URL that the next deploy writes into every job, and the alert channels (with their tokens), without the 5-minute re-authentication that other host-facing changes need. It doesn't run anything on a host directly, so this is low. *Fix:* mark it `@password_confirmed` for consistency with rule 13.

## Docs in code

- **D1.** The `server.py` module docstring lists `/api/deploy/start` kinds as `jobs|shares|changes`; the code also accepts `tasks`.
- **D2.** In `server.py`, the `# planner designs` comment sits above the `/api/access` routes, and `f'deploy.start'` is an f-string with no placeholders.
- **D3.** The `scriptkit.py` docstring says `--host` forwards your SSH agent; it now does so only with `--forward-agent`.
- **D4.** `deployments-design.md` gives job ids as `<plan-slug>-<step-id>`; the code uses `p<plan>-<step>`. It also predates storage tasks as a deploy kind and the machine-id check. It is a design record, so add a note at its top pointing to [Deployments](deployments.md) for the current behaviour rather than rewriting it.

## Tests

**T1.** `test_indexer.EndToEnd.test_unreadable_folders_and_duplicate_folders` makes a folder unreadable and expects the scan to report it. On a machine where read-only scan access is installed (`/usr/local/lib/storageforge/find` carries `CAP_DAC_READ_SEARCH`), the scan uses that `find` and reads the folder, so the test fails. *Fix:* skip when those tools exist, or have the test force the plain tools.
