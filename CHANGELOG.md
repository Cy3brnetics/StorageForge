# Changelog

Newest first. Releases are tagged `vX.Y.Z`, and a fix to a release `vX.Y.Z.N`. Everything before 0.3.0 was 0.2.0 and was never tagged.

## Unreleased

### Security

- **Every destructive step in an Ansible export now runs only with `-e storageforge_destructive=true`, as the playbook's header says.** The exported tasks of seven destructive steps had no such gate, because each step module writes its own export: creating an mdadm array, installing or removing an OS on a disk, moving a tool's data to the trash, reverting a VM to a snapshot, removing a workload and rolling a ZFS dataset back. A plain `ansible-playbook` ran them. They now carry the `destructive` tag and the gate, whichever module wrote them, and a test walks every destructive step type.

### Fixed

- **Signing out while the page is still drawing its first answers no longer raises a script error.** When answers to the page's first load arrive, the infrastructure view waits 50 ms to draw them all at once. A sign-out inside those 50 ms let that drawing run on the emptied page. It now stops once the page is signed out. 0.6.3.1 fixed a similar case for answers still being read; GitHub CI's slower runners hit this one in three browser tests.

### Changed

- **The Ansible task of a bridge, VLAN, MTU, SSH option, AppArmor, SELinux or AppArmor setup, NTS time, WireGuard, workload action or removal, or ZFS rollback step carries only the Bash it runs.** Each such task held about 500 lines of other steps' functions, because the pattern that cut out one helper ran to the end of the text; the tasks of the network address, bond, route and DHCP steps held their interface guard twice. The tasks now carry the function they run and each helper it calls once, and do the same on the host.
- **A secret name that starts with a dot, a dash or an underscore is refused by the check of the Tailscale, Cloudflare Tunnel, Pangolin site, NetBird, OpenZiti and LUKS steps, and by `vault send-secret` and `vault secret-add`.** Those steps and commands allowed such a name, but the vault never stores one and a plan's apply never delivers one, so the step passed its check and then found no secret on the host. The message now says a name starts with a letter or digit. Both commands now refuse such a name as a usage error, exit code 2, where they failed with 1 (`vault secret-add` after reading stdin, `vault send-secret` after looking the name up).
- **A step parameter missing from a saved plan reaches the step's Bash function in an Ansible export as an empty word, not the word `None`.** This happened in the exports of the LUKS, network, infrastructure, libvirt, VM, VM from ISO, ZFS hold and disk image steps, for a plan saved before a field was added.
- **A check of an rclone mount step finds rclone at /usr/bin/rclone when the PATH it runs with does not include it**, as an apply and the WebDAV and S3 share mounts already did. It said rclone was missing and would be installed, and the apply then found it installed.

### Internal

- The Ansible task that runs a step's Bash function is built by `changes.shell_task`, its parameters become words by `changes.words_of`, and helper functions are cut out of a Bash text by `changes.bash_fn`, in place of copies in 28 step modules. Each task still carries every helper it runs (BE-35).
- The first line of an exported step's Bash (`APPLY=1` and the `ok`, `missing`, `conflict` and silent `info` helpers) comes from `changes.ansible_head` in the eight step modules that wrote it out identically: Tailscale, VM disk folder, secret file, desktop, OS install, rclone mount, netconsole and container runtime. The exported text is unchanged (BE-36).
- The secrets folder on a host (`secretstore.SECRET_DIR`) and the rule for a secret's name (`secretstore.NAME`) are defined once, and the check of a step's secret field is one `secretstore.secret_ok`, in place of copies in the Tailscale, tunnel, overlay, LUKS, secret file, share and Nebula modules, the plan field check and the CLI. Generated scripts are unchanged (BE-38).
- The OS install and VM from ISO steps download and check their image with `sf_vm_fetch`, the function the VM and Proxmox VM steps already used, in place of a copy of its body each. The plan script already carried it; the VM from ISO step's Ansible task now carries it too. Messages and files are as before (BE-39).
- A scan's package list is read by one `scriptkit.package_facts` (on `scriptkit.package_words`) for the package check of a deploy preview and for the host preflight, and the reinstall script takes its btrfs, NFS, SMB, sshfs, NFS server and Samba package names from `scriptkit.NEEDS` through `scriptkit.need_tuple`, which `need_line` also uses. Generated scripts are unchanged.
- The SFTP, WebDAV, NBD, NVMe-oF and virtiofs share drivers make the folder a share serves with one `share_dir` in the driver helper set (`netshares.BASH`), in place of the same line in each. The shares script prints the same messages as before (BE-41).
- The rclone options that hold a password, key or token are one `rclone.SECRET_KEYS`, read by the rclone mount step and the rclone serve share, and what a check (no apply) says of an rclone client mount is one `rc_mount_report` in the rclone library, used by the rclone mount step and the WebDAV and S3 client mounts. Their messages are as before (BE-42). The check of the rclone mount step now finds rclone as its apply does (see Changed).
- The lossless archive codecs (their file ending, the tool each needs and whether it streams) are one table in `scriptkit` (`CODECS`, `CODEC_EXT`, `CODEC_TOOL`, `STREAM_CODECS`, `codec_tool`), read by the archive step, Moves, the storageforge-job package checks and `archive create`, in place of a table, a list and string tests on `xz-extreme` in five modules.
- The idle wrapper `sf_idle`, the rsync wire compression probe `rsync_compress_flags` and the round-trip verified compressor snippet `sf_remote_compress_cmd` are one Bash kit, `scriptkit.COMPRESS_KIT`, that Moves scripts, storageforge-job and the change-plan archive step each carry whole, in place of three copies of the first, two of the second and two of the third. The text sent over SSH to a compression host is the same, and the job program's rsync flags come out in the same order; the job program's text changes, so the next deploy to a host that runs jobs rewrites its storageforge-job.
- Tasks are staged as a named change plan by one `changes.stage`, which finds the plan by its name in any case and makes it when there is none; the caller chooses whether new tasks replace the plan's own (security hardening, re-converge, roll back, labels, AppArmor, fences, a map design) or are added after them (a step from the map, a Linux host's firewall rules), in place of the same lookup written in three modules (BE-45).
- A host's deployed mark for a unit is dropped by one `deploy.forget_deployed` (one unit, or every unit of a kind), and the hooks that run after a deploy open and close their connection with one `deploy.hook_conn`, in the tasks, schedules, ClamAV, decoy, jobs and receiving-key modules, in place of a hand-written delete and close in each. Which runs mark or forget is unchanged (BE-46).

## 0.6.3.1 — 2026-11-26

The fixes for GitHub CI's test jobs, which had failed since 0.6.0 on PostgreSQL and since 0.6.2 on SQLite: two product bugs found that way are fixed below, and the rest were tests written for SQLite only or for a fast machine. Checked here (GitHub has not run it yet) with every block on SQLite and light and medium on PostgreSQL 16. The image scan job still fails on vulnerabilities in the key enclave's kernel and the Wolfi base, which needs a decision of its own.

### Fixed
- **Signing out no longer leaves a half-read answer to draw on the emptied page.** Signing out empties the page before `/login` loads. An answer whose headers had arrived but whose body was still being read could then run its handler on the empty page, which raised a script error (seen once on GitHub CI). Reading a body after sign-out now never finishes, as the request itself already didn't.
- **A long answer from a network device no longer slows the session in the square of its length.** Reading from a router or switch over SSH or telnet cleaned all the output received so far every time more arrived, to find the prompt on the last line. A megabyte took about 15 s on a fast machine and over 30 s on a slow one, where a command could time out; the 64 MiB cap was out of reach. Only the last line is cleaned now, and the whole answer once, when the prompt arrives. Found when GitHub CI's test of the cap timed out.

### Tests
- The archive, storage manager, clone and two bug-hunt tests run on PostgreSQL: they put integer timestamps and fixed ids where PostgreSQL wants a timestamp and picks the id, or read a JSON column as text. Three that drive a SQLite file through `--db` or back one up are skipped there, as the CLI tests already are.
- The key enclave's unlock limit test asks for a wait only when the time the attempts took has not earned them back: on a slow runner nine attempts take long enough to earn a ninth.

## 0.6.3 — 2026-11-26

The second version of the [0.7.0 roadmap](roadmap-0.7.0.md): 24 small pieces of shared work (parsers, SSH key handling, path tests, database spellings, host names) written once instead of in several modules. Most change nothing a user sees; what they do change is listed under *Changed*. Built and unit-tested on SQLite (light, medium and heavy blocks); **not lab-tested**, and not run on PostgreSQL in this release's checks. One browser test of the key enclave page failed once in three heavy runs and passes alone: it is a known flaky test, not fixed here.

### Changed

- **A `@revoked` or `@cert-authority` line in StorageForge's `known_hosts` is no longer read as a host's pinned key by sync jobs and scan signatures.** Jobs copied such a line into the job's own `known_hosts` with its fields shifted, so ssh ignored it, and a receiving host with only such a line counted as pinned when a send to it was deployed, then failed later with a less clear error. Such a host is now refused at deploy as one with no pinned key. Scan signatures listed it as one of the host's keys. Both now skip marker lines, as host fingerprints and host certificates already did, and a job's `known_hosts` no longer carries the comment that followed a key.
- **Scan signatures find a host's keys in the same cases as the rest of StorageForge.** For a host with no port set or an address written in brackets, the scan looked for the wrong name in `known_hosts` and found no host keys. It now names the host as every other reader does, and ssh-keygen runs without StorageForge's own environment variables, as elsewhere.
- **The container step's check and the what-if, Terraform and Puppet exports read the ports to publish the same way.** A part that is not `[address:][host-port:]container-port[/tcp|udp]` with ports from 1 to 65535 and a real address (`ab:cd`, `70000:80`, `8080:80/ud`) made the what-if, the design's Terraform and Puppet exports and the plan's Terraform, OpenTofu and Puppet exports fail with `invalid literal for int()`, or was carried into them as written. Now it is left out of all of them, and the container step's check warns that it is not checked. A port published with no host port (`9000` or `127.0.0.1::9000`), which Docker and Podman give a host port of their own choosing, is no longer checked against what listens on port 9000; it is still warned about when it is open to every network.
- **The ClamAV deploy finds a host named with spaces around it, and an empty host name never stands for a host.** The ClamAV deploy refused ` nas ` as not scanned where the security actions and host certificates took it as `nas`; now it takes it too. An empty name could stand for a host whose recorded address was empty; now all three checks refuse it, each with its own error (not scanned, or no host by that name for host certificates).
- **A run log line nested too deeply to parse no longer stops a scan's reading of that host's runs.** A line in a host's `runs.jsonl` with thousands of nested brackets made the scan's reading of sync job runs, deploy confirmations and task runs fail with a recursion error. It is now skipped like any other bad line, as the schedule runs already were.

### Internal

- The `@@section` output of the network facts, OpenWrt, pfSense and infrastructure readings is split by one function, `netfacts.split_sections` (BE-11).
- SSH wire strings and key fingerprints are written by one stdlib-only module, `sshwire`, in place of copies in eight modules. The agent receiver's signature check and the scan signature reader keep their own parsers (BE-12).
- The keys pinned for a host in `known_hosts` are read by one function, `remote.known_host_entries`, in place of four `ssh-keygen -F` parsers in the fingerprint lookup, host certificates, sync jobs and scan signatures (BE-13).
- *Is this path under that folder* and *which mount holds this path* are answered by one pair of functions, `paths.is_under` and `paths.deepest`, in place of three containment tests and three deepest-mount loops. The planners' copy took an empty or relative path to be under `/`; now no relative path is under any folder, as the SSH side already ruled. Every caller passes an absolute path, so nothing a user sees changes (BE-14).
- The `\NNN` octal escapes of fstab, mountinfo and findmnt are decoded by one function, `remote.unoctal`, in place of copies in the fstab readers of payloads and the host config history and in the findmnt reader. A design version's size text is written by `capacity.fmt_bin`; it is the same text up to 1024 PiB, and a size beyond that now reads in EiB where it read in thousands of PiB (BE-15).
- The three hash terms of a folder's fingerprint are written once, in `folders.file_term`, `folders.folder_print` and `folders.child_term`, for the per-mount folder index and the per-subtree compare of folder copies. The per-file loop of the mount index keeps its file term inline for speed, with a comment that points at it (BE-20).
- The first-level folders under a path, with their sizes, are listed by one query, `moves.first_level`, for the Moves folder picker and the file map. Each keeps its own handling of mounts below the path and its own answer for a host that was never scanned (BE-21).
- The platform readers share one module, `apiparse`, for loading JSON answers, taking the list or the `data` of an envelope, the bounded readers of untrusted values and the date reader, in place of copies in Xen Orchestra, TrueNAS, Dockhand, Portainer, Komodo and the Proxmox readers and read-backs. Pangolin keeps its own envelope reader, which needs `data` to be an object and reads the page total (BE-16).
- The Proxmox Backup Server and Proxmox Datacenter Manager readers read the `/version` answer with the Proxmox VE reader's `parse_version` in place of their own copies (BE-17).
- The *ports to publish* text of the container step is read by one function, `steps_workloads.parse_publish`, with one record shape, for the what-if, the design's Terraform and Puppet exports, the plan's workload exports and the container step's check, in place of four parsers. The Incus step keeps `incus_ports`, which refuses an IPv6 address its proxy devices can't take (BE-18).
- A secret in network-language output (a WireGuard private key) is hidden by one function, `rostranspiler.redact_text`, for a device change's report and the compile preview, and `rostranspiler.secrets_of` decides whether a change's source may be stored. The refused RouterOS line keeps its own `***` marker (BE-19).
- *The interface that carries this address* is found by one function, `exposure.iface_of`, for a device change's SSH check, the plan what-if's SSH checks and the reach model, and the controller's addresses for a check that goes on without them come from one function, `security.controller_ips`, in place of two nested wrappers. The three SSH checks keep their own verdicts (BE-33).
- The default gateways of a network reading are listed by one function, `netfacts.gateways_of`, for a host and the RouterOS, OpenWrt, pfSense and Cisco adapters, and a dotted netmask is turned into a prefix length by `netfacts.prefix_of_mask` for the Cisco and SNMP adapters (BE-34).
- The shares script opens ufw for NFS, SMB and the other share kinds with one function, `ufw_allow`, which `open_fw` and the drivers' `open_port` both call. The firewalld branches stay apart, and every message is the same (BE-22).
- The Proxmox steps look up the guest the last reading holds under a VMID with one function, `steps_proxmox._guest_at`, and the container and VM create steps check a new VMID with one function, `steps_proxmox._new_vmid`. Every message is the same (BE-29).
- Every container of a host, from the scan's stacks and the rootless Podman of the last reading, is listed with how it runs by one function, `workloads.containers_with_how`, for `workloads.containers_of` and the Toolbox adapters' context (BE-30).
- The SQLite-or-PostgreSQL spellings `ts`, `distinct` and `jsonp` live on one class, `db.Dialect`, that both the connection and the database have, so code holding only a connection no longer writes `to_timestamp` or the `jsonb` cast by hand (the agent's monitoring-only inventory, its file index updates and the monitoring-only host setup). `Database.sync_mounts` needs only the connection, and the agent's monitoring path calls it without the stand-in it passed as `self`. The SQL is the same text (BE-23).
- A host's short name is worked out by one function, `hostid.short`, which `moves.host_slug` and `db.short_name` now name, and the host-name pattern of plans and of key installs is one, `hostid.HOST_RE`, which `scriptkit.HOST_RE` and `keyinstall.HOST` name. The known-host checks, the host lookup by address and the other host patterns are left as they were (BE-24).
- A typed host name or address is turned into the scanned host by one function, `deploy.known`, behind the three known-host checks of the security actions, host certificates and the ClamAV deploy. Each keeps its own error and text (400 or 404). `deploy.canonical` still hands back what it was given when nothing matches (BE-32).
- A host's JSON-lines run log is read by one function, `confirm.jsonl_dicts`, for deploy confirmations, task runs, sync job runs and schedule runs, in place of four loops. Each caller keeps its own field checks (BE-25).
- The protocol constants written once in the controller's Python and once in the agent, wire and enclave Rust (frame size, Noise names and prologues, batch limits, signature namespaces, the agentctl operations, magic line and exit code, the agent's user and root groups, the enclave's vsock port) are compared by one test, `tests/test_wire_constants.py`, which reads the Rust sources without cargo. It also checks that the agent's inventory scan writes only sections the SSH scan's parser knows (BE-26).
- A kernel line from netconsole or pstore is built by one function, `hostlogs.kernel_line`, with its message cleaned by `hostlogs.kernel_message`, and the `side` status row they both need is written by one, `hostlogs.ensure_side_status`. Each keeps its own priority prefix and line key (BE-27).
- The agent's record queue is cleared by one function, `agentplugins.forget`, with one batch size, `agentplugins.RECORDS_PER_TICK`, for the pushed log lines and the plugin readings. The wipe reports keep their own drain and limit (BE-28).
- The label `reported by agent` is defined once, `agentwatch.LABEL`, which the disks, files and scan plugins and the monitoring-only host setup now name. Which plugins a host's manifest names was already answered by one function, `agentwatch.plugins_by_host`, since BE-06 (BE-31).

## 0.6.2 — 2026-11-26

The first version of the [0.7.0 roadmap](roadmap-0.7.0.md): the ten places where a backend consolidation survey found that one copy of shared work was wrong. Built and unit-tested on SQLite (light, medium and heavy blocks); **not lab-tested**, and not run on PostgreSQL in this release's checks.

### Security
- **A platform certificate that changes in the middle of a read fails the whole read.** Each request already refused the new certificate and sent nothing, but the read-backs and the readers of Xen Orchestra, Pangolin, Portainer, Komodo, Dockhand and parts of the Proxmox ones wrote that refusal down as one more thing they could not read. The read then counted as good: the connection did not say *certificate changed*, no finding was raised, and what the calls before the change had returned (with Xen Orchestra, Pangolin or Portainer possibly nothing) replaced the last good reading. Now the read fails, the connection says *certificate changed* with the fingerprint that was offered, the critical finding is raised, the last good reading stays, and no further request is made on that read.
- **A platform certificate that changes while a new token is checked refuses the rotation and is recorded.** Rotating an API connection's token tries the new token against the platform first. A changed certificate met there was reported as "the platform did not take the new token", and the connection was not marked: the critical finding came only with the next read. Now the rotation is refused with the reason, the connection shows the certificate it was offered, and the finding is raised at once. A change met by the forgiving expiry lookup is caught too. The old token stays in place either way.
- **An NVMe over TCP mount formats a disk only when `blkid` says it is blank.** The client's helper script ran `mkfs` whenever `blkid -p` printed nothing. It prints nothing for a blank disk (exit status 2), and also when it finds conflicting signatures (8) or cannot read the disk (4), so a mount with a format set could format a disk that held data. Now the helper formats only on status 2, as iSCSI and NBD mounts do, and on any other failure it stops with `blkid could not read ... not formatting it` and the unit fails. The helper's text changes, so each NVMe over TCP mount is unmounted and mounted again once, on the next deploy of its shares. Built and unit-tested, not lab-tested.
- **Storing a secret or a device credential no longer replaces a credential of another kind that has the same name.** Secrets for plan steps, device credentials and the tokens of API connections are rows of one table in the vault, and storing one deleted whatever row had its name. `vault secret-add`, `vault headscale-key` and `POST /api/devices/credentials` did not look first, so a secret stored under the name of a switch's credential, or a device credential stored under `api-proxmox-pve`, replaced it without a word and the device or the platform could no longer be reached. Now each refuses a name that a credential of another kind holds and says which kind: the two commands end with status 1 (`headscale-key` before it makes a key on the server), and the route answers 400. The route also refuses to store a device credential again under the user name `secret`, which would have turned it into a secret for plan steps. A secret is still replaced by `secret-add`, and a device credential by the route, which is how its password changes. `vault headscale-key` over a secret that had a policy dropped the policy, so the new key was released for any step and host: it now keeps it. A secret replaced by either command keeps its creation time and records when its value changed.

### Fixed
- **Retiring a host removes what was left behind.** Retire deleted a host's security events, measurements and quarantine list, but not its security readings (the Lynis and compliance trend), its ban history, the map's snapshots of it, the waivers and retention policies made for that host alone, or its compliance drift and session watch settings. Those stayed in the database, and a host later added under the same name inherited them: an old waiver hid a finding on the new machine. Retire now removes them all, without regard to the case of the name, and its result and audit entry count the waivers and retention policies that went. A waiver or policy made for every host (`*`) stays, as do the audit log, deploy history and design versions. What retire removes is now one list, and a test reads the schema and fails when a table that names a host is neither on it nor listed as kept with a reason.
- **A Xen Orchestra host with no address is no longer taken for a scanned host that has no address either.** When a host in Xen Orchestra matched no scanned host by name and its API answer carried no address, the empty address was looked up among the scanned hosts' addresses, and a scanned host whose address was never recorded matched. Its VMs were then listed and drawn on that unrelated host, and the storage comparison read that host's mounts. Now a host with no address is matched by name only, and a scanned host with no address is matched by no address.
- **A container managed through a platform API is named by the platform's title.** A container that a Portainer, Dockhand or Komodo connection manages was said to be managed by `portainer`, the connection kind, while one told by its labels was said to be managed by `Portainer`. The Workloads page showed both spellings, and a plan check on a stack whose containers were known both ways could warn about the same panel once for each spelling. Now both say `Portainer`. The `api.platform` field of a workload is still the connection kind.
- **One host's unreadable agent manifest no longer stops alerts for other hosts.** The controller keeps the manifest it last signed for each host's agent and reads it to know which plugins the host runs. When one host's stored manifest was not JSON and that host was monitoring-only, the two alerts of the agent's scan plugin (*the agent's scan and the SSH scan disagree*, *has not sent its inventory*) stopped for every host, and each alert pass wrote a traceback to the error log. When it was JSON of another shape (a list or a number where the manifest's object should be, or `plugins` that is not a list), the alert pass itself failed, so no alert of any kind was opened, refreshed or resolved until the row was repaired. Now the three places that read a manifest share one reader, and a manifest it cannot read names no plugins: that host gets no *has not sent its inventory* or heartbeat alert, and every other host's alerts go on. The controller writes these manifests itself, so this needed a damaged or hand-edited row.
- **A network scan that a restart cut short is no longer shown as running.** A scan's row was closed only by the scan itself, so when the controller stopped or was restarted in the middle of one, the list of runs on the **Scan** page went on showing it as running until twenty later runs had pushed it out of the list. New scans were not held back by it, but an open **Scan** page that was waiting for the scan went on asking for it every four seconds. Now the controller closes such a row when it starts, as it does for deploys, change runs and file scans: the run is listed as failed, and until the next scan the page opens on it and says `This scan failed: interrupted by restart`, as it does for any failed scan.
- **The tunnel, private network, restore test and Toolbox steps no longer reload systemd past a dead network mount.** The Cloudflare Tunnel, Pangolin site and Nebula steps, the timer of a restore test and the socket drop-in of a Toolbox package ran a plain `systemctl daemon-reload`. On a host with a hard NFS or CIFS mount whose server is gone that reload waits, and every new login waits with it. Now they reload through the same check the share and move scripts use: the step stops with a conflict naming the mount that is not answering, before the unit is enabled or started and, for the socket drop-in, before it is written. A tunnel stopped by a dead mount no longer also says *did not stay running*. Removing a tunnel, a timer or a drop-in still removes it and reports the reload it could not make. The tunnel token and the Pangolin site secret are removed before that reload, so the Ansible task, which a conflict ends, does not leave them on disk. A restore test with a timer also reloads systemd on an apply that writes nothing when its timer is off or systemd says it has not read the units, so units a refused run left unread are read on the next one; a timer that is on and read is not reloaded, so a dead mount does not fail a restore test step that has nothing to do. A reload that fails for another reason while a unit is being set up was ignored and is now a conflict (a tunnel reports it as not staying running); on removal it is still not reported. The Ansible tasks of these steps carry the same check. Built and unit-tested, not lab-tested.
- **The tunnel and private network steps read a secret from the folder the plan delivered it to.** A plan run as root writes its secrets to `/run/storageforge/secrets` whatever the variable `SF_SECRET_DIR` says, and so does `vault send-secret`. The Cloudflare Tunnel, Pangolin site, NetBird and OpenZiti steps read the folder the variable named, also as root. On a host where root's environment set it, the secret was delivered to one folder and the step stopped with `no tunnel token at ...` (or setup key, site secret, enrollment token) for another. As root these four steps now read `/run/storageforge/secrets`, as every other step does. The variable still moves the folder for a run that is not root. Built and unit-tested, not yet lab-tested.

## 0.6.1 — 2026-11-26

### Security
- **The agent's setup refuses a managing user in a root group again.** The check that stops the setup when the manager or agent account is in `docker`, `wheel`, `sudo` or another group that is root on the host piped `id -nG` into `grep -q` under `pipefail`: on a match, `grep` stopped early, the writer was killed by SIGPIPE, and the failed pipe skipped the refusal. It now loops over the groups with no pipe, the same with GNU and the Rust coreutils.

### Fixed
- The test suite passes on Ubuntu 26.04 with the Rust coreutils, as GitHub CI runs it: tests that reached the real `systemctl` or `systemd-run` on the machine running them use stand-ins (one asked polkit to start `sf-fw-rollback`), the archive tests write their log under their own folder, the agent receiver tests wait for the receiver to have the agent's key instead of a fixed time, and two tests that only passed where a tool was installed or a label was older are corrected.

### Docs
- The README and docs describe 0.6.0 as built: the docs index lists every page, the web UI page names the Workloads page, and statements that called built features "not built" are corrected, each checked against the code.

## 0.6.0 — 2026-11-26

The work the roadmap planned for 0.5.5 to 0.5.16, released together. Much of it is built and unit-tested but **not lab-tested**: each such item says so below and in `roadmap.md`. The PostgreSQL migrations of this release have not been run against PostgreSQL in this release's checks.

### Fixed
- Requests no longer wait on the reverse proxy's name lookup. With `STORAGEFORGE_PROXY_HOST` set, a slow container resolver made sign-in, the first page and periodic host refreshes stall about 8 s at a time. The lookup now runs once at start (bounded) and then in the background.
- A task's "host up" condition only takes a host name, and the generated check passes it to bash as data. Free text there ran as root on the host without `hosts.command`.
- Playbooks read an event's client and pid only from fields the event itself set. A file or process name the host observed (Falco, sentinel) can no longer choose the address to ban or the process to kill.
- Tool data folders written with `.` or `..` (`/./etc`) are refused like the system folders they name.

### Security
- **A Toolbox step runs only from an entry that is still trusted and still the one staged.** A catalog update needs the release key and a higher serial; an entry may enable only its own units and install only its own program, and an override cannot put a volume in a system folder.

A redirect is followed only to another API path on the same server. A Dockhand token without an enterprise key, a Portainer Community Edition user, and any admin or write-capable token are findings that cannot be muted.

Installing a key from Keys, and rotating one, write `restrict,pty` before it, and `from="…"` when `STORAGEFORGE_SSH_FROM` names the controller's addresses. Scans now read which options each key line carries, names only, and two warnings follow: a StorageForge key with no restrictions, and a StorageForge key in an account in `docker`, `lxd`, `incus-admin`, `wheel`, `sudo`, `admin` or `libvirt`, which makes the web app root on that host in effect. Keys installed before this keep their bare line until installed again.
- **`storageforge-update apply` installs nothing without a signers file,** unless `STORAGEFORGE_UPDATE_TRUST_REMOTE=1` is set for that run; the shipped timer unit now sets `STORAGEFORGE_UPDATE_SIGNERS`. A signed tag must also name the release it is stored as, so a signed old release pushed again under a newer version is refused, and a tag with no signature is refused. The update lock moved from a predictable name in `/tmp` into the clone's `.git` folder.
- **A console VM name can no longer start with `-`,** and the name reaches `virsh` after `--domain`, so it is never read as an option.
- **A platform token is released only for the platform it was stored for,** checked inside the key enclave when there is one; `root@pam` tokens and plain HTTP are refused, and a token never appears in a log, an audit row or an error.

- **An agent's report can cause only its own revocation.** Anything wider is held for a person unless an independent witness agrees, and every action a report caused or asked for is kept with its witnesses.
- **An agent's container reaches only the receiver's address and port,** through a host nft rule loaded before the container starts and at boot (matched on the bridge and `sfagent`'s uid, not the cgroup).
- **An agent that names another machine than SSH reads is a security finding that cannot be ignored.** A plugin that declares privileges, and accepting a new receiver key, need the new `agent.privilege` permission (admins only). On SQLite the receiver has no database role, only a limit on its connection, and in the Docker setup it runs as the web app's user.

The old private key is deleted at a rotation, a second key nobody asked for is a notification and is never taken, and the console no longer offers *the StorageForge network* because an interface happens to be called `sf0`.
- **A `cloudflared` or `newt` started with its token as an argument is named in the Security overview.**
- **The channel to the key enclave is encrypted** (Noise NX), with the enclave's key pinned at first start.
- **Sensitive requests carry a code that changes every 30 seconds, in their path** (`/api/~<code>/…`). A reverse proxy rule that matches those URLs exactly must allow the segment. It is checked by the server, not inside the enclave, which has no clock to share with a browser.
- **The session-signing key rotates daily and the vault key is rewrapped every 30 days.** To allow that, the enclave holds the vault secret from unlock to lock.

- **The proxy runs nginx 1.31.9, which fixes two memory-corruption bugs in HTTP/2 that anyone who can reach port 8443 could trigger before logging in** (CVE-2026-123007 and CVE-2026-123633, published 2026-11-18). ### Added
- **A plan step that starts, restarts or stops one service** (`unit-state`, under Software in Changes). It enables and disables nothing, so what starts at boot stays as it was, and it refuses SSH, the network and the firewall, which are done by hand on the host. It is what a prepared fix for a failed service is made of.
- **Log rules: a notification when a host logs something worth one.** A rule matches lines by host, unit, program, lowest level and text, with a threshold over a window, as each scan brings lines in; one alert per rule and host, so a flood is one alert, resolved when the count falls back. Ten built-in rules for storage hosts: out of memory kills, disk and controller I/O errors, ext4, XFS and btrfs errors, a degraded ZFS pool or md array, an NFS or SMB server not responding, failing services, crashing programs and a full disk, with bursts of failed SSH and sudo logins off until turned on. Patterns are text with `*` and `|`, never a regular expression over what a host wrote. A rule about a program goes by who journald saw write the line. **Rules** in the Logs panel and `/api/hostlogs/rules`, the permission `hostlogs.rules` for operators and admins, migration 045. Rules see what scans collect, so a line is matched at the next scan.

A notification can be acknowledged with a note, snoozed for up to 30 days, or muted by host and kind. **A critical notification, drift and a security finding cannot be snoozed or muted**, and a mute never covers one: they leave when resolved, and are always pushed. A snooze ends when a notification becomes critical, which is pushed again. The history keeps every opening and resolving and who did what. A new permission, `notifications.manage`, which operators and admins have; migration 044. **A notification can carry a prepared fix,** offered only where there is a way back: a service that keeps failing gets *Restart it*, which is saved as a change plan and opened in Changes, where its report is read and its deploy takes the password as any plan's does; *Prepare the way back* makes the plan that stops it again. ### Fixed
- **A busy host on an older systemd lost its newest log lines, for good.** A scan keeps at most 5,000 routine lines and 2,000 warnings from a host. Before systemd 254, `journalctl --since … -n` gives the first lines since then, not the last, so on Ubuntu 22.04 and Enterprise Linux 9 a host that had logged more than that sent its oldest lines, and the next scan started after the ones it never sent. The journal is now read newest first, which takes the newest on every version, and what is over a limit is the oldest, as the note always said. Found in the KVM lab, on systemd 249 and 252.
- **A folder made to receive btrfs copies is root's alone (SF-72).** `btrfs receive` keeps the owner, mode and setuid bits its stream carries and cannot drop them, and the lab showed another account on the receiver reaching a root setuid file in a copy. A folder a receive makes is now mode 0700. One that was there already keeps its mode, so copies you share or browse stay as you set them: [Security](docs/security.md#sends-between-hosts) says what to do for those. ZFS was already safe, and the lab now reads that back.
- **A flood from one host costs the flood, not its older lines.** Each host has a rate, by default its row limit spread over its days (16,666 lines a day, with one day saved up). Lines over it are not stored, routine ones before warnings, and the Logs panel and `/api/hostlogs/status` say how many. `STORAGEFORGE_LOG_RATE_PER_DAY` changes it.
- **A host's clock no longer decides which of its log lines are kept.** Lines were kept or dropped by the time the host stamped on them: one stamped older than 30 days was deleted as it was stored, so a host with a wrong clock kept nothing, and a host could log lines stamped a day ahead and have them push its real lines out of the row limit. Lines are now kept by when they arrived. Migration 043 runs on start.

- **The package list knows image-based, transactional and read-only systems, apt on rpm, and Debian's holds, backports and local packages.** Fedora Silverblue, Kinoite, CoreOS and bootc systems give the packages layered onto their image (and name the image); MicroOS and Aeon install through `transactional-update`; SteamOS and Ubuntu Core give only their apps; ALT Linux and PCLinuxOS are their own family. - **A VM panel for libvirt hosts.** **Infrastructure → Workloads**, then a VM: its state, vCPUs, memory, firmware, guest agent, disks and snapshots, with buttons that stage a plan step: start, shut down, restart, force off (new in `workload-action`), snapshot, revert, delete a snapshot, change, copy to another host, console and remove. Under each libvirt host are its networks and storage pools, each to change or remove, and new ones. Scans now read each VM's snapshots, guest agent, machine type and CPU mode, and each network's and pool's state, autostart and room. `GET /api/workloads/libvirt`. See [VMs on libvirt](docs/vms.md).
- **Snapshots done properly: `vm-snapshot` and `vm-revert`.** Disk-only by default, with the filesystems frozen first by the guest agent when it answers (`--quiesce`), refused when **require** is set and it does not, and crash-consistent without it. Delete merges a disk-only snapshot back. Revert is destructive. Going back to a disk-only snapshot takes a libvirt that does it (12.9 does; 10.0 and 9.0 refuse), and a refusal is said as such, with the VM left as it was. On libvirt before 11.10 the overlays of a VM that is off are made readable by root alone (CVE-2025-13193). Internal and disk-only snapshots are never mixed on one VM, as libvirt then cannot delete them. `workload-action`'s snapshot is disk-only too. `vm-create` can install the guest agent (**Install the guest agent**).
- **VM snapshots and backups on a schedule: the `vm_snapshot` and `vm_backup` task blocks.** Snapshots named `<prefix>-<date>`, the newest N kept per VM, and never one another prefix or a person made. Backups are a whole qcow2 per disk and the definition, in `<into>/<vm>/<date>/`, root-only, taken from a disk-only snapshot of a running VM that is merged back after. Two templates.
- **Changing a VM: `vm-edit`.** vCPUs, memory, autostart, a disk added, grown (never shrunk) or detached (its file kept), with an optional clean restart so vCPUs and memory change now. A rerun changes nothing.
- **libvirt networks and pools: `libvirt-network` and `libvirt-pool`.** Define, change and remove a NAT, routed, isolated or bridged network with its address and DHCP range, restarted on request. Define, move and remove a folder, LVM or ZFS pool. One that a VM uses is refused removal, and removing a pool leaves its files.
- **Copying a VM as it is to another libvirt host (migration phase 6).** `vm copy`, `POST /api/vm/copy` or **Copy to another host…** saves two steps:
  - **`vm-send` on the source.** Each disk goes through a signed send of its own, with a new `vm` receive tool: a new file, root-only, sparse, checked by SHA-256 on both ends, never written over. It is taken live from a disk-only snapshot merged back after, or with the VM off.
  - **`vm-define` on the target.** It defines the VM from the source's reading, with no XML from the source, and new MAC addresses unless asked.
- **All of the above ran in the lab on 2026-11-09:** tier 18, 17 of 17, on libvirt 10.0 and 9.0 with a nested guest, including a live copy between the two hosts that booted. Going back to a disk-only snapshot ran only on libvirt 12.9, outside the lab. See [Lab run](docs/vms.md#lab-run).

### Security
- **A host's report can no longer write holds or quarantines, or make the worm check pass (SF-70).** A `brake_ran` line from a host is only an event now. The signed brake run writes the rows, and checks each value first.
- **A host with a report token can no longer fill the database (SF-73).** At most 300 events an hour per host and 100 of any one kind, detail cut at 2,048 characters, an `events_dropped` warning once an hour, and old acknowledged events pruned.

- **Scan payloads are signed on the host and checked before they are used.** Everything a scan reads from a host (the inventory, each folder walk, the checksum pass, the journal, the network, container and git surveys) comes back with a signature over a fresh nonce and the SHA-256 of exactly the bytes the host sent, made with `ssh-keygen -Y sign` in its own namespace. A payload that does not verify, was signed by another key than the one pinned for that host, or differs from what was signed, is refused: a refused walk leaves its mount's index as it was, and a refused inventory stops the scan before job runs, ClamAV results or security events in it are taken in. - **One long log line can no longer hold the server (SF-52).** The host-log scrubber's first two patterns read on from every character of a long run of word characters, so one 4,000-character line took 0.7 seconds and a line made of the word `pwd` over and over took 2.5 minutes, with every web request waiting. ### Security
- **Backup copies on another host are encrypted**, with a key from the vault secret. They hold password hashes and alert tokens. `restore` takes them as they are. Without the vault secret, no copy is made.
- Invite and reset links die when their role comes to allow more. A reset link also dies when its account is replaced or changes, and a new link cancels the last one. **Open links made before this update stop working: make them again.**
- `backups.manage` and `settings.manage` are marked high risk. A retired host can't still have schedules. A job's `.git` link can't point outside its source.
- A Git repository can no longer run code as the scan account through its own config. Git runs with those settings off, and `git status` runs only in repositories the scan account owns; others show **Not checked**. Git routes take only repositories a scan found.
- **Git sync needs deploy access.** Sync is now a signed run, as the repository's owner, with hooks off and a fresh password for every action. Git status, history and commit are POST only, rate limited and audited.
- The log fetch after a failed task refuses odd task names and no longer copies all of `/var/log/messages`.
- A task's timer no longer rewrites the deploy runner. **Redeploy existing tasks**: copies already installed keep doing it until then.
- Raw commands need a new high-risk permission, `hosts.command`, to write or deploy: command schedules, a task's **Run command** blocks and **command succeeds** conditions, and a move step's pre and post commands. Only `admin` has it by default, so operators who use them need a custom role. A move's `docker compose -p <name> stop` and `start` hooks stay open to `plans.edit`, and anyone can take commands off a host. Env variables that change what runs (`PATH`, `LD_*`, `BASH_ENV` and others) are refused.
- Downloading a schedule's install script no longer rotates its token: the file carries none, and that host reports through scans. A failed deploy no longer ends the old token. Reports never go to an address taken from a request's Host header: set a report URL, or runs arrive with the next scan.
- Bad or slow verify patterns can no longer lose a report or hold a web thread, and repeated report nonces are ignored.
- **Schedules no longer run on the StorageForge server.** The **Run local** button and `{"local": true}` are gone: they let an operator run commands where the vault secret lives. Use `storageforge-index schedule run` from a shell on the server.
- Creating, changing, pausing, running or deleting a schedule, and rotating its token, now asks for a fresh password. Running one also applies the deploy preflight.
- Schedules can no longer run destructive steps, which bypassed `deploy.destructive`. A schedule deployed with them keeps its old script until redeployed: it shows as changed on the Deploy tab.
- A schedule installed on a host can't be deleted until it is uninstalled. Ones already deleted get an **Uninstall** button on the Deploy tab.
- Git routes no longer run on the server when given `host=localhost`. Loopback names need a key bound to them, like any host.
- Accounts that can't edit schedules no longer see their commands or env values. Run output needs `logs.view`. Alert addresses in `/api/deploy` need `settings.manage`.
- `viewer` can no longer download a schedule's install script (which also minted a report token), its cron line or a host configuration bundle. These now need `plans.scripts`.

- `zfs set` works on Ubuntu 22.04's ZFS, which rejected `--`.
- A job's verify no longer counts ssh warnings as differing files, and a failed rsync is reported as such. **Redeploy existing jobs.**
- Podman's overlay folder is skipped as image layers, so it no longer makes a scan partial.
- A scan records mergerfs's branch folders as its source, not `1:2`.
- **Files in nested btrfs subvolumes are now indexed.** A subvolume inside a scanned mount, without a mount of its own, was silently left out, along with all its files. The next scan adds them. Read-only snapshots stay out.
- Single-device btrfs filesystems now get the same scrub and device error checks as pools. Their results were dropped, so expect new scrub warnings on hosts with the collector.
- File map: faster, kept until the index or ignore list changes. Ignore lists are no longer capped at 4 KiB, and saving one no longer holds the request while graphs rebuild.
- Schedule runs are pruned to the newest 200 per schedule.
- **The backup copy to another host** now goes through the signed runner. As written it could not get past the deploy key's forced command.

### Changed
- **Schedules run from a bash script, without Python.** A systemd timer fires it, or cron where there is no systemd. With no flags the install script only reports. **Redeploy every schedule:** the old Python runner stays in charge on a host until then, and redeploying removes it.
- **A schedule's `verified` now means a scan newer than the run agrees.** Until that scan a run is `reported`. A required path that's missing now fails the check instead of warning. Output no longer goes in the world-readable `runs.jsonl`, so runs picked up by a scan have none.
- **Schedules:** pausing and resuming now update the host, and alerts keep watching until it has. Reports up to 512 KiB are accepted (they were refused above 4 KiB). Drift and dry-run checks notice a change to the plan a schedule runs, so **every deployed schedule shows as changed once after this update: redeploy it.** `nice`, `ionice`, jitter, timezone, window and `user` now take effect; `catchup` and the `scan` task type are gone. A plan or task made for another host can't be scheduled on this one. Cron now wakes the runner every minute and the runner decides.

### Added
- **Invite links and permissions:** admins create single-use, expiring links that let someone make their own account with a role chosen in advance, and password reset links replace email. Roles now bundle about 30 permissions in groups. `viewer`, `operator` and `admin` stay as they were and cannot be edited, there is a new built-in `search` role that can only search files, and admins can create custom roles. Nobody can grant more than they hold.
- **Graph view, Files map:** Graph now opens on an expandable node map of every host's files, from the index. Tick cards and copy them to any folder on any host by clicking it or dragging onto it, or move, sync, snapshot, rename, trash or change owner. Copies and syncs go in the Moves plan and draw as blue lines, and copy steps can now take single files. Lines show what is already joined: copies, symlinks, bind mounts, shares, jobs and backups. Each line lands on the deepest open card, so it follows down as you expand, and cards show how much under them is duplicated. **Duplicates** shows only the folders with copies, where you can trash the extras: the last copy of anything cannot be staged. The force-directed graph is still there under **Structure**.
- **Ignored paths:** system folders, packaged apps in `/opt`, rsnapshot rotations (`daily.0`), container layers and StorageForge's own trash stay out of the file map, and dangling symlinks in those places no longer turn a host red. Add your own with **Ignored…** or **Ignore this link** from the topology or graph, or start a line with `!` to show something again.
- **Unified Task Scheduler & Client Runner:** A scheduler that can schedule any task StorageForge can do (Storage task block pipelines, Change plans, Move/Sync plans, Host inventory scans, and Commands). Tasks can be scheduled with standard 5-field cron expressions or aliases (`@daily`, `@hourly`, etc.), with rich configuration options (execution windows, concurrency policies `skip`/`queue`/`replace`, timeouts, retries with backoff, nice/ionice priorities, environment variables, and alerting). Execution can run via native cron files (`/etc/cron.d/`) or a lightweight client daemon/runner (`storageforge-scheduler`). Client execution reports back via bearer tokens to `/api/scheduler/report`, where the server conducts comprehensive post-execution verification (authenticity, exit code, required/forbidden output regex patterns, mount integrity, free space thresholds, and filesystem path existence against the StorageForge index). Management is provided via REST APIs (`/api/scheduler/*`) and CLI (`storageforge-index schedule`).
- **Disk health:** rerun the read-only scan access setup to install an hourly collector for SMART and btrfs errors. The scan account gets no new rights; scans read its report. Failing disks, pool errors and overdue scrubs raise alerts and show in the topology and report.
- **Backups found by scans:** restic, borg and rsnapshot folders, ZFS and btrfs snapshots and snapper configs now show in the 3-2-1 matrix, marked as detected.
- **Capacity history:** each scan records how full every mount is. The Cleanup tab shows 30-day trends and "full in about N days", which can raise an alert.
- **File changes and identical files in the Cleanup tab,** and an alert when one scan finds many files gone.
- **Report sections** for deployed jobs with their last runs, storage tasks, open alerts and drift, capacity trend, shares, unreadable folders, git repositories and containers.
- **Backups in the web UI**, with an optional copy of each backup to another host over SSH. A failed copy raises an alert.
- **Roles and accounts in the web UI:** change your own password, and admins can add, disable and remove accounts. `viewer` browses and searches, `operator` also plans, scans and deploys, `admin` also handles keys, accounts and settings. Existing accounts stay admins.
- **Retire a host** from its menu or with `hosts remove`, and remove keys and bindings from the Keys tab.
- **Per-host scan schedules:** a host can have its own interval and quiet hours, from its menu in the topology.
- **Designs stage pool tasks:** a new ZFS pool, ZFS datasets, a new LVM volume group and its volumes now become change-plan tasks instead of "by hand" notes.
- **3-2-1 matrix from what is deployed:** mirror and rsnapshot jobs and scheduled storage tasks fill the sync, snapshot and backup cells with their last good run. Typed values stay where nothing covers a dataset, and hosts can be marked offsite.
- **Move progress:** a move script run by hand now shows "copied" and "cut over" on its steps after the next scan.
- **Moves:** Duplicate and Export JSON. **Git:** select repositories and archive them together, and hide or show paths per host.
- **Storage tasks on the CLI:** `tasks list`, `check`, `script` and `import`.
- Storage task checks warn when a running container uses a block's source or destination.
- Shared test cases keep the planner's and the report's capacity numbers the same.
- **Shares manager in the topology:** a Shares button lists every share on the hosts in view, with access, client mounts, state and check problems, and opens designed shares to edit or remove. Editing and removing now find a share by its identity instead of its list position, which could change after a rescan and hit the wrong share. Wizard edits keep SMB settings and per-client mount options, a deployed share can be removed from the design, and saving a second copy of a share is refused.
- **Deploy run tracking and scan confirmation:** Scans verify completion records of deploy scripts (`/var/lib/storageforge/run/runs.jsonl`) and storage tasks (`/var/lib/storageforge/tasks/`) by matching run nonces, confirming actual host outcomes. If a run or task failed, StorageForge automatically runs a signed read-only log fetch over deploy access once per problem to capture runner and journal logs.
- **Deploy cancel and retry:** Running deploys can be stopped in the UI (with a Force stop option to terminate running SSH processes), and failed or interrupted deploys offer a Retry failed hosts button.
- **Stale dry run protection:** Applying a plan passes the dry run's group ID to ensure the plan was not modified after review.
- **Host configuration history and reinstall scripts:** each scan saves a host's fstab, crypttab, mdadm, NFS and Samba files, mounts, accounts and cross-mount symlinks when they change, with passwords removed. The new Rebuild tab and `storageforge-index config` show versions and what changed, and export a script that mounts every drive and subvolume on a fresh install, plus a `.tar.gz` to keep elsewhere. `STORAGEFORGE_CONFIG_EXPORT_DIR` writes that bundle every night.
- **Parallel scans:** up to `STORAGEFORGE_SCAN_WORKERS` hosts (default 4) scan at once, so a large or hung host no longer holds up the rest.
- **KVM lab:** `examples/lab` builds seven disposable VMs, picked at random from 14 configs across distros and filesystems, with a local control panel to create, reset and destroy them, StorageForge running on one VM, a demo that fills it with scans, shares, jobs and an alert, and test tiers including btrfs in depth, with a report per distro ([KVM lab](docs/kvm-lab.md)).
- **ZFS change tasks:** create a pool, create a dataset with properties, snapshot, scrub.
- **LVM change tasks:** create a volume group, add a device to one, create, grow and snapshot a logical volume.
- **Send over the network:** `btrfs-send` and `zfs-send` change tasks, and `btrfs_send` and `zfs_send` storage task blocks that send only the changes since the last shared snapshot, with "btrfs replication" and "ZFS replication" templates.
- **Alerts** for failed scans, missing mounts, nearly full filesystems, unhealthy pools and device errors, failed or old backups, and an expiring HTTPS certificate.
- CI for Forgejo Actions, ruff settings, `.env.example`, and guides for disaster recovery, troubleshooting and target hosts.

### Fixed
- **Container vulnerabilities:** the runtime image moved from Debian 12 to Debian 13 and installs Debian's security updates at build time. It no longer carries apt, perl, bash, tar, gzip, util-linux, PAM, Kerberos, ncurses or the sqlite3 shell, none of which it uses; `docker compose exec storageforge sh` still works. The ssh client is built from OpenSSH 10.6p1 because Debian 13's 10.0 has unpatched holes, so DSA host keys no longer work, as with any OpenSSH from 10.0. The proxy moved from nginx 1.27 to 1.30 pinned by digest, with its Alpine packages updated and curl removed. Grype on the runtime image: 5 critical and 84 high before, 0 critical and 13 high after.
- **Smoother Deploy tab:** Deploy panel polling updates output in-place preserving card expansion and scroll position; active deploys resume polling across tab reloads; the reporting settings form is kept across reloads; and deploy access removal uses a secure inline form instead of a plain-text prompt.
- An apply from the web UI rescans the hosts it ran on, so the other tabs show the result instead of waiting up to 6 hours for the next scan.
- A change plan that finished applying is no longer staged and moves to "Already ran" in the picker: deploy tracking ID matching is type-coerced, local drafts preserve clean state across reloads rather than forcing dirty state, and plans whose changes already exist on hosts offer one-click unstaging and mark as ran. Editing a plan makes it a plan to run again; one that skipped drive tasks stays unfinished and says so.
- An apply that left `missing` steps shows as `incomplete` instead of a green `ok`, for every kind of deploy, and a later scan keeps it that way.
- Share, change and move scripts run by hand end with "N step(s) not finished" instead of `done` when an apply left `missing` steps.
- A shares apply that left steps on the server is no longer marked as deployed.
- Move plans deployed as jobs are grouped under "Deployed as jobs" in the picker, until they are edited.
- Open tabs reload once the rescan after an apply ends.
- A refused deploy no longer fails with an internal error when it writes to the audit log.
- The git survey finds repositories when the host runs it with `dash`, instead of reporting none.
- `jobs.py` used f-string syntax that only Python 3.12 and later accept, though `pyproject.toml` promises 3.10.
- Two vault key derivations at once could hang, leaving deploys stuck and later scans failing with "Not enough memory to derive key" until a restart. They now run one at a time.
- A restart now marks unfinished deploy runs as failed, as it already did for scan jobs, instead of leaving them shown as running.
- `scan --host 127.0.0.1 --port 2222` scanned this machine instead of the SSH server on that port.
- Piping CLI output into a command that stops reading, such as `head`, no longer shows a traceback.
- Operations described a web backup button that does not exist.
